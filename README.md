# 三进制 vs 二进制 · GPU 位并行筛选

同一份 Rust 代码、同一个 GPU、同一条查询，只换数据表示：

| 实现 | 每对象表示 | 线程粒度 | 耗时/次 | 吞吐 | 带宽/次 |
|---|---|---|---:|---:|---:|
| **BINARY** | 3 个 f32 | 1 个对象 | 0.0373 ms | 26.8 M 对象/s | 12.0 MB |
| **TERNARY** | 6 bit（pos/neg 位平面） | **32 个对象** | **0.0194 ms** | **51.6 M 对象/s** | **0.38 MB** |

**1.92× 快**，命中数两版完全一致（74,209），不是偷工减料。

## 直观对比

打开 `index.html`（纯静态页面，双击即可）：

- 左右两个面板同时扫描 1 万个示意格子
- 左边逐对象比较，右边每 32 个一批
- 命中格子高亮，底下实时显示进度条

## 为什么是 1.92×，不是 32×

位并行度是 32，存储密度比也是 32，但只拿到 1.92×：

1. **12 MB 完全落在 4060 Ti 的 L2（32 MB）里** —— 二进制版根本没被显存带宽卡住
2. **GPU 的 f32 比较本来就便宜** —— 位运算省掉的 3 次比较在 20 TFLOPS 的卡上微不足道
3. **1M 对象只跑 0.037 ms** —— 已接近 kernel 启动下限

要看到真正的带宽差距，需要 1000 万对象以上（120 MB，超出 L2）。这个还没测。

## 实现

查询：`a == True && b == True && c != False`（3 个三值条件）

**BINARY**（纯 f32，无任何三进制依赖）：

```wgsl
if (a[i] > 0.5 && b[i] > 0.5 && c[i] > -0.5) {
    atomicAdd(&counter, 1u);
}
```

**TERNARY**（位平面）：

```wgsl
// 一个线程处理 32 个对象
let bits = pa[w] & pb[w] & ~nc[w];
let n = countOneBits(bits);
if (n > 0u) { atomicAdd(&counter, n); }
```

## 测量口径

- 批量 dispatch 200 次后统一 `poll(Wait)`，不在每轮里 `clear/copy/poll`
  （每轮的固定开销约 0.1 ms，会把差异完全盖住——初版就是这样，只测出 1.15×）
- 位平面用 32 位字（`u32`），不是 64 位：`1u32 << (i % 64)` 会溢出，
  初版因此少算了 5675 个对象
